# Model validation findings

Found while generating the backend from the 82-table model. Each needs a decision; the backend
currently implements the model as written unless noted.

| # | Finding | Severity | Current handling |
|---|---|---|---|
| 1 | `approval_request` has no "requested by" column, so the DB cannot enforce maker-checker | High | Added `requested_by_user_id`, `requested_by_agent_run_id`, `decision_note` in `model/extensions.json`. Push back into the artifact. |
| 2 | Employee self-service has write on its own `employee` row, including `is_active`, `department_id`, `position_id`, `legal_entity_id`, `date_of_joining`, `date_of_exit` | High | **Resolved (Sprint 12a).** Confirmed exploitable: a signed-in employee could deactivate themselves or change the `legal_entity_id` payroll derives the tax jurisdiction from. `grant_caps` in `model/extensions.json` caps the employee role at READ on every `employee` column except `personal_address`; generated `0024_model_grant_caps.sql` REVOKEs the rest (0003 is untouched). HR-owned fields change through `tenant_hr` or `employee-record-writer`. `tests/test_employee_self_service.py`. Push the cap back into the artifact. |
| 3 | All agents share one grant set (`agent_runtime`); per-domain roles exist but are not narrowed | Medium | The model's worker map names workers, not their domains. Add a worker → domain map, then generate narrower per-domain grants. |
| 4 | 18 tables have no writing worker (reference data and employee-only tables) | Medium | Need owners: admin UI, seed, or human-only service. List in `docs/backend-plan.md`. |
| 5 | Enum columns (88) have no value lists | Medium | Stored as `text` without checks. Add value lists to the model, then generate CHECK constraints. |
| 6 | Daydor ops "assigned tenants only" is not modelled | Medium | **Resolved (Sprint 13b, `0037`).** `app.ops_tenant_assignment` (admin assigns and revokes; never deleted) and `app.tenant_id()` returns a `daydor_ops` session's tenant only for an assigned, signed-in user, otherwise NULL, so every tenant policy, default and tenant-filtered function gets the check. Ops with no tenant is a platform session; ops with a tenant and no user sees nothing. Other roles, including `daydor_admin`, are unaffected. The API's seed assigns its ops user. `tests/test_ops_scope.py` |
| 7 | Aggregate-only access (level 1, e.g. founder on `self_identification`) needs report-specific views | Low | **Resolved for the EEO-1 report (Sprint 13c, `0038`).** `app.eeo1_report(p_min)` is a SECURITY DEFINER function (so it obeys tenant row security and the ops assignment check) returning counts by job family, race or ethnicity and gender over current employees; a cell under five people comes back with its count withheld, the minimum cannot be lowered, and there are no totals to subtract from. Only the roles whose access is aggregate-only (ops, founder, HR, auditor) and the `eeo-report-builder` worker may call it; nobody but the employee can read a raw row. Other reports need their own function in the same shape. `tests/test_aggregate_reports.py` |
| 8 | `approval_request.required_approver_role` is single-valued; several gates allow more than one approver role (e.g. `g_pay_anomaly`: payroll or ops) | Low | The gate registry stores the full approver list and the DB trigger checks against it. |
| 9 | Managers have read-only access to `approval_request`, but timecard and expense approval routers send approvals to managers. No gate in the model lists the manager as an approver | Medium | Approvals resolve through `app.resolve_approval()` against the gate registry. Add manager-approved gates (e.g. `g_timecard`, `g_expense`) to the model to enable these flows. |
| 10 | `employee`'s 4 encrypted columns (Aadhaar e-KYC ref, PAN, SSN, bank account) are modelled NOT NULL, but encrypted columns carry no INSERT grant for any role (ADR-002), and `consent_record.employee_id` needs an employee row to reference before consent can be captured. No role can ever insert a conforming `employee` row as modelled | High | Relaxed the 4 columns to nullable in `migrations/sql/0012_hire.sql` (a documented deviation from the generated DDL, not a `ddl.py` change). `employee-record-writer` (`src/daydor/hire/employee_record.py`) creates the row with them NULL; they are populated afterwards via `app.encrypt_pii`, once `consent_record` rows exist. This matches the flow's own step order (`employee` is step 10, `consent_record` is step 12). Push the nullable columns back into the artifact. |
| 11 | No gate in the model covers requisition budget sign-off, though the hire flow's "approval_request W requisition-approval-router" step needs one | Medium | Added `g_requisition_budget` (approver: founder) as a platform-defined hard gate in `src/daydor/gates/registry.py`'s `PLATFORM_HARD_GATES` (distinct from `SOFT_GATES`, same idea), seeded by the regenerated `0007_gate_seed.sql` for fresh installs plus an incremental `0013_platform_gates.sql` for already-migrated databases. Push back into the artifact. |
| 12 | `id` columns never carry an INSERT grant for any role (every table's id is DB-generated by convention), so a workflow instance's subject cannot be a row whose id is allocated after the instance starts | Medium | `daydor.hire.requisition.open_requisition` creates `job_requisition` with a DB-generated id *before* `WorkflowEngine.start()` is called against it (see `daydor.hire.workflow.start_hire`); the two model steps that would otherwise run first (position check, requisition draft) run synchronously ahead of the instance and are represented as pass-through states (no `enter_jobs`) purely so the transition log still shows them in order. Any future flow with the same shape (a step before the subject row exists) needs the same treatment. |
| 13 | `s04_job_posting`'s "advance" auto-fired in Sprint 1's definition, but nothing about "a posting is live" implies "a candidate exists" | Low | Removed the auto-fire from `handle_job_posting_publisher` (Sprint 2). `daydor.hire.screening.submit_application` is the real trigger, fired whenever a candidate actually applies. This was correct in Sprint 1 (the very next state was "done"); it stopped being correct once Sprint 2 extended the graph past it — a reminder that "this step auto-advances" is only safe when verified against the *current* graph, not assumed from an earlier version. |
| 14 | `WorkflowEngine._move()` entered the new state using the pre-transition `inst.context` instead of the freshly merged context from `fire(..., context_patch=...)`, so a context_patch passed alongside an advancing transition never reached that transition's own `enter_jobs` | High | Fixed in `src/daydor/workflow/engine.py`: `_enter()` now takes an explicit `context` parameter, and `_move()` passes the merged context through instead of relying on the stale `inst` snapshot. Generic engine bug, not hire-specific; affects every flow that patches context and advances in the same `fire()` call. |
| 15 | The hire flow's own step 19 (`payslip`, "First cycle") cannot be built as part of the hire flow: `payslip.payroll_run_id` is NOT NULL, and `payroll_run` is a per-period batch covering every employee on it, built end to end by the Payroll flow's own sprints (anomaly detection, `g_pay_anomaly`, `g_pay_disburse`). There is no "just this one employee's first payslip" shortcut that doesn't duplicate or fake that machinery | Medium | The hire flow's engine-driven graph permanently ends at step 18 (`payroll_profile`), not step 19 (`src/daydor/hire/workflow.py`, version 6, `0018_hire_workflow_v6.sql`). The employee's first payslip is whatever Payroll Sprint 8 (`payroll-run-builder`) produces once a cycle including them runs. The model flow's name ("Requisition to first payslip") describes the employee's end-to-end journey across flows, not one flow's sole responsibility to produce it. |
| 16 | `benefit_election`'s table-level grant shows `E: WRITE` (looks like employee self-service, same shape as `consent_record`/`time_punch`), but `coverage_tier` and `employee_cost` are C2-class with the employee's own column access at READ, not WRITE -- the table-level grant is a summary, not the real per-column picture | Low | Confirmed by the model naming a real worker (`election-processor`) for this table, which the genuinely self-service tables don't have. `daydor.benefits.election.elect_benefit` runs as `agent_ben`, not the employee's own session. General lesson: a table's summary grant level is not sufficient evidence that a column is writable by that role; check per-column `access` before assuming "self-service, no agent" for any table. |
| 17 | `payslip_line.payslip_id` is NOT NULL and `payslip.payroll_run_id` is NOT NULL -- the same shape as finding 15, one level down. A `payslip_line` cannot exist until a real `payroll_run`/`payslip` exist | Medium | `daydor.payroll.compute.compute_gross_to_net` (Sprint 7) returns a plain result object instead of row ids; it computes, it does not persist. Sprint 8's `payroll-run-builder` calls it and writes `payslip_line` rows once it has created the `payroll_run`/`payslip` rows to attach them to. |
| 18 | Every numeric column in the generated DDL is `numeric(14,2)` (`daydor.model.ddl.SQL_TYPE`'s blanket mapping) -- correct for currency amounts, but it silently rounds statutory rate *fractions* to the nearest 0.01: a real FICA rate of 0.0765 (7.65%) was stored as 0.08, a ~4.6% relative error in a legally mandated withholding. Caught by a test asserting an exact computed amount, not by inspection | High | Widened `statutory_rate_rule.employee_rate`/`employer_rate` specifically to `numeric(8,6)` (`0020_statutory_rate_precision.sql`) -- a documented deviation from the generated DDL, not a `ddl.py` change (rates vs. amounts need their own physical-type distinction in the model to generate correctly; that's an artifact change). Worth auditing other numeric columns the model treats as rates/percentages rather than currency the next time one is touched. |
| 19 | `payroll_run.gross_total`/`net_total` and `payslip.gross_pay`/`net_pay`/`tax_withheld` are modelled `derived` -- `ddl.py`'s `grants()` correctly excludes every `derived` column from every role's INSERT/UPDATE grant (not even `agent_runtime` gets one), but nothing in the model or the generated DDL supplies an alternative way to *set* a derived column once a role needs to write it for real, the same gap encrypted PII columns have (finding 10) | Medium | `migrations/sql/0021_payroll_run_functions.sql` adds `app.open_payroll_run`, `app.record_payslip` and `app.finalize_payroll_run` -- SECURITY DEFINER functions, same pattern as `daydor.privacy.pii`'s `encrypt_pii`/`decrypt_pii`. `app.finalize_payroll_run` recomputes `payroll_run`'s totals by summing the `payslip` rows already written, rather than trusting a second, possibly-drifted copy of the same number from the caller -- the database derives the value, not just gates who may claim it. Push back into the artifact: a `derived` column needs the model to also say how it gets computed (an aggregate over a named table, or an opaque business-logic input), not just that it is one. |
| 20 | `final_settlement.approval_request_id` is modelled NOT NULL and `total_settlement` is `derived` -- the same "can't reference what doesn't exist yet" shape as findings 10/19, but also: the model's own `g_pay_disburse.tables` list names `final_settlement` alongside `payroll_run`/`contractor_invoice`, yet the generated `gate_guard` seed tied `final_settlement.disbursed_at` to `g_finalpay` instead (the amount-approval gate, not the disbursal gate); and `cobra_event.notice_sent_at` had no `gate_guard` at all despite `g_cobra` existing for exactly that action | Medium | `migrations/sql/0022_exit_gate_guards.sql`: relaxed `approval_request_id` to nullable; added `app.open_final_settlement` (SECURITY DEFINER, same pattern as `app.open_payroll_run`); corrected `final_settlement.disbursed_at`'s guard to `g_pay_disburse`; added `cobra_event.notice_sent_at`'s `g_cobra` guard. `g_finalpay` is instead a workflow-level checkpoint in `daydor.exit.workflow` (no column of its own to guard), the same role `dpdp_consent` plays in the hire flow. Push back into the artifact: fix the `g_pay_disburse`/`g_finalpay` guard-column assignment and add `cobra_event`'s missing guard. |
| 21 | `POST /hire/start` accepted a hire without the fields later steps read with bare `ctx[...]` lookups (`employment_type`, `legal_entity_id`, `proposed_base`, ...). The hire started, then a worker job `KeyError`ed at employee creation, retried, and dead-lettered while the hire sat at that step | Medium | Fixed in the API layer: `REQUIRED_AT_START` in `daydor_api/routers/hire.py` rejects the request with a 422 naming the missing fields (checked after the 403, so a role that cannot open a requisition still gets 403). The backend handlers still use bare lookups: a direct caller of `start_hire()` gets the same late failure. |
| 22 | `start_hire()` / `start_exit()` were not idempotent: `engine.fire()` only skips duplicates when given an `event_id`, and their startup `"advance"` calls had none, so a replay advanced the live instance's current state (exit skipped from the legal-hold check straight past the checklist) or raised `WorkflowError` (hire) | High | Fixed: both fire their startup advances with fixed `event_id`s (`start:<instance>:<n>`), so a replay returns the existing instance and moves nothing. Regression tests fail without the fix. Any future `start_*()` must do the same. |
| 23 | Same shape as finding 2, wider: the employee role holds column-level UPDATE on workflow-owned columns with no gate guard -- `timecard.status`/`approved_by_user_id`, `expense.reimbursed_at`/`gl_journal_entry_id`/`approval_request_id`, `leave_request.status`/`fmla_designation`/`approval_request_id`, `benefit_election.carrier_sent_at`, `checklist.status`, `life_event.status`, `training_assignment.completed_at` (verified against live grants) | High | **Resolved (Sprint 12b).** `grant_caps` entries (same mechanism as finding 2, folded into the generated `0024`): employees are read-only on `timecard` and `checklist` and `training_assignment` entirely, and lose only the system-owned columns on `expense` (`policy_flags`, `approval_request_id`, `reimbursed_at`, `gl_journal_entry_id`), `leave_request` (`status`, `fmla_designation`, `approval_request_id`), `benefit_election` (`carrier_sent_at`) and `life_event` (`status`, `window_closes_at`); they keep what they author (expense category/receipt, leave policy/dates/reason, life-event facts, benefit plan/dates). The gate guards on `expense.reimbursed_at` (`g_expense`) and `leave_request.fmla_designation` (`g_fmla`) were added later (`0031`, ADR-006, finding 29); `leave_request.status` is deliberately unguarded. Push the caps back into the artifact. |
| 24 | **Agents could never collect or decrypt PII.** `app.current_app_role()` returns `agent_runtime` for every `agent_*` role, but `app.pii_column.collect_roles` and `app.pii_purpose.allowed_roles` (0011) list `agent_hr`, `agent_ob`, `agent_pay`, and the checks were `current_app_role() = ANY(...)`. Confirmed live; no test exercised PII as an agent | High | **Resolved (Phase 1).** `0027` adds `app.current_actor_role()` (the real role name: the agent or worker role, else the people role) and `encrypt_pii`/`decrypt_pii` compare that. `0028` seeds worker roles into both registries (`PII_COLLECTORS`, `PII_PURPOSES` in `daydor.agents.roles`).
